# Triage with Jev

This is the Specgate intake for the project issue tracker. It uses the same
states as Matt's triage skill, and it does not publish a label, comment, or
close until the maintainer confirms.

Read the tracker's own instructions and label map (`docs/agents/issue-tracker.md`
and `docs/agents/triage-labels.md` when this repo has them). If the map is
missing, stop and ask for it. Do not invent label strings.

Canonical states: `needs-triage`, `needs-info`, `ready-for-agent`,
`ready-for-human`, `wontfix`. Categories: `bug`, `enhancement`. An item carries
one category and one state. Conflicting states stop the run until the
maintainer picks one.

PRs are in scope only when the tracker says they are a request surface. This
repository's tracker says they are not. An explicit number the maintainer names
is still in scope.

## Show what needs attention

When the maintainer asks what needs attention, list three buckets, oldest
first, with a count and one line each:

1. Unlabeled.
2. `needs-triage`.
3. `needs-info` whose reporter replied after the last triage note.

Do not relabel while listing.

## Triage one item

1. Read the issue (body, comments, labels, author, dates). For a named PR,
   read the diff too. Skip questions the existing triage notes already
   resolved.
2. Search the codebase by domain concept for an existing implementation.
   Read `.out-of-scope/*.md` for a prior rejection. Report where you looked.
3. Recommend one category and one state. Say why, including whether the
   behavior already exists.
4. Verify the claim before grilling. A bug is reproduced from the reporter's
   steps. A PR is checked out and its relevant checks are run. Record
   confirmed, failed, or insufficient detail.
5. Call `jev_verify` on the recommendation. Claims use stable IDs
   `{issue}:category` and `{issue}:state`. Evidence is the issue text, the
   codebase finding, and the verification result. Do not send secrets or
   harness transcripts.
6. A missing calibration manifest does not stop this skill. Do not tell the
   maintainer that Jev is offline or unusable because of it. Without a manifest
   the result carries `calibrated=false` and `gate.basis=confidence_policy`; the
   score is an uncertainty filter, not measured accuracy. `verified` means
   the claim passed. `auto_advance` false only forbids applying the board
   with no confirmation. Mock, contradicted, error, a result without
   `gate.basis`, and a confidence under the policy threshold do not apply a
   label.
7. Show the recommendation and wait. Apply labels only after the maintainer
   confirms the exact transition. A confirmed `verified` transition is applied.
   Do not refuse it for lack of calibration.

## Outcomes

- `ready-for-agent`: post an agent brief. Before posting, `jev_verify` the
  brief's acceptance criteria as `{issue}:brief-{n}`. The brief states current
  behavior, desired behavior, interfaces, acceptance criteria, and out of
  scope. No file paths, line numbers, or session identifiers. A large or
  unsettled scope does not get a thin brief: send it to `grill-with-jev`,
  then `to-spec-jev`.
- `ready-for-human`: same brief, plus why an agent must not take it
  (authorization, external access, or a judgment the maintainer kept).
- `needs-info`: post what is already established and the specific questions
  still owed by the reporter. Do not ask them to "provide more info".
- `wontfix` because it already exists: comment with where the behavior lives.
  Do not write `.out-of-scope/`.
- `wontfix` because an enhancement is rejected: after confirmation, write or
  update `.out-of-scope/<concept>.md` with the decision, the reason, and the
  issue link, then close.
- `needs-triage`: apply the label. Comment only when there is partial progress.

A maintainer override ("move #42 to ready-for-agent") skips the grill. Confirm
the label change, then ask whether they still want a brief.

Do not close issues, merge, or deploy except the `wontfix` close the
maintainer just confirmed. Do not post that the note was generated by a
model.
